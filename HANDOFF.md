### 2026-10-02 RTMP(S) publishing never could have worked: four protocol bugs, now covered by `RtmpPublisherTest` (a local fake ingest)
1. A read timeout while waiting for the next server message threw. Reads are capped at 1 s, so the quiet period after releaseStream/FCPublish aborted every connect. Now a timeout on a message's first byte means "no message"; the rest of a started message gets 10 s.
2. `connect` sent its properties (app, tcUrl…) after a null command object. They are now the command object.
3. `publish` went out on message stream 0; it now goes on the stream id from createStream (chunk stream 8).
4. AMF0 booleans were written as a bare 0x01 (true) or 0x02 (false, the string marker). They are now a marker plus a value byte.
5. On the device, YouTube's 240-byte connect `_result` failed with `length=240 index=240`. The AMF0 reader read an ECMA array's `count` entries but left its 00 00 09 end marker unread. Fixed: ECMA arrays and objects share `properties()`; types 6 (undefined) and 0x0C (long string) are added; and a value that can't be parsed no longer fails the command. The test's fake server now sends a chunked, YouTube-shaped reply with an ECMA array. With the old reader it fails the same way (`Index 225 out of bounds for length 225`).
6. The first live test (2160x3840@60, 40 Mbps) published to YouTube, then the connection dropped about 10 s after each Publishing. Likely cause: the decoder setup (AVC/HEVC sequence header, AAC config) was only forwarded as the encoder's one CODEC_CONFIG sample. It was lost if it arrived before `onFormat`, and never re-sent after a reconnect. Now the publisher keeps the latest setup, sends it first on every connection, gates video on a keyframe and asks the encoder for one (`onKeyframeNeeded`). This is covered by `startsEveryConnectionWithTheDecoderSetupThenAKeyframe`. A reader thread runs while live: it answers pings (user control 6→7) and logs server onStatus/_error/close. Acks now count bytes received, not sent. `writeMessageRaw` takes the write lock. Each connect resets the inbound chunk state. The drop reason now goes to the log. Not yet confirmed on YouTube.
6b. **Root cause of YouTube refusing the stream** ("live streaming isn't available", server closes after about 15 s): the FLV `AVCDecoderConfigurationRecord` was malformed. `extractCodec` kept MediaCodec's Annex-B start codes on csd-0/csd-1, so the profile and compatibility bytes were read from `00 00`, and the level byte was missing, which turned 0xE1 into the length-size byte. Fixed: the bare SPS/PPS are picked by NAL type (some encoders put both in csd-0) and the record is written per spec. `startsEveryConnectionWithTheDecoderSetupThenAKeyframe` now checks the exact record bytes and the 4-byte-length frames.
6c. HEVC chosen in Output but the stored profile still said H264 (checked via run-as on the device DB). Probable cause: a stale settings round-trip. SettingsViewModel saves in the background and Room re-emits; an older emission landing after a newer change replaced it, and the next change saved the stale codec. Saves are now serialized (Mutex) and emissions are ignored while saves are pending.
6d. Stop while Connecting did nothing: `StreamOutputSession` stored `rtmp` only after the blocking connect, and the engine used `session!!` that Stop cleared. The publisher is now stored before connecting, `RtmpPublisher.stopRequested` aborts a connect between steps, the engine uses a local session plus `startCancelled` (a cancelled start ends IDLE, never LIVE), and the button shows Stopping…. No confirmation is asked for a stream that isn't live.

Monitoring silent: the monitor AAudio stream had no error callback, so after a device change (dock unplugged, BT headphones) it stayed dead; inputs were only marked inactive. `NativeAudioMixer::recoverStreams` (mix thread, at most once a second, backoff 1→30 s) reopens a lost monitor or inputs on the current device. `stop()` joins the mix thread before closing streams.
6f. Media source died with `ERROR_CODE_DECODING_RESOURCES_RECLAIMED` (Android gave its decoder to another app, likely YouTube Studio). It now re-prepares with backoff.
6g. **Stream audio was near-silence with bursts of distortion** (the media source was the only input). `HardwareAudioEncoder` read the mixer's native-order float buffer through `duplicate()`, which resets to big-endian, so every float was byte-swapped. 6v. **Audio mixer rebuilt (native_audio_mixer.cpp), for garbled audio with two sources playing.**
   - **Bug 1, stale start time.** `Ring::startPts` was set only when a ring went from empty to non-empty, never advanced on pop/discard. With 2+ inputs the mixer aligned on stale times, saw one source as behind, and discarded nearly all of its buffer every block. Now `popUpTo`/`discard` advance it before releasing frames.
   - **Bug 2, no clock.** `mixLoop` emitted a block whenever any one source had data, so sources arriving at different moments became extra half-mixed blocks, faster than real time. The encoder queue overflowed. It is now clocked like OBS's audio thread:
     - one 10 ms window per tick, 50 ms behind now;
     - each input contributes the samples stamped for that window; late ones are dropped (`lateFrames`), early ones wait;
     - short windows are zero-padded (`shortWindows`);
     - a block goes out every tick while anything is routed to the stream.
   - **Bug 3, clipping.** Two near-0 dB sources summed past full scale and were hard-clipped. A stream-mix limiter now runs: −1 dBFS ceiling, instant attack, 80 ms release, stereo-linked.
